# 选题管理规格

状态：讨论中。第一版使用方式已确认；分组命名和下述具体行为为建议，尚未整体确认。

日期：2026-09-10

本文件是功能需求草稿，不代表选题管理功能已实现。初始真实选题单独保存在本地 `content-projects/_planning/2026-09-10-topic-management-initial-topics.md`，该记录不进入 Git，在其他项目副本中可能不存在；它不是一期文章项目，不作为 `content prepare` 的输入。

## 问题与目标

作者近期想写的帖子和选题增多，需要在当前项目中集中记录，避免想法遗忘，并能按内容方向查看、选择下一篇和继续补充素材。选题将服务于公众号和小红书创作，开始写作后接入现有每期独立内容项目的流程。

用户已确认第一版采用项目内选题库，通过 Codex 记录、分组、查看和更新，先不做管理页面。

## 已确认范围

- 在当前项目内管理选题，保存用户提供的题目和写作角度。
- 支持分组；当前考虑 LLM、Harness，未来还要有围绕企业业务落地的 Agent 分组。
- 首批有两个选题，详见上述本地初始选题记录。业务 Agent 当前没有具体题目，不自动补造选题。
- 第一版以本地文件和 Codex 对话作为使用入口，不开发本地网页或线上管理后台。

## 分组建议

分类依据是文章主要回答的问题。分组是编辑组织方式，不要求构成概念上完全互斥的技术分类。

| 分组建议 | 主要回答的问题 | 内容范围 | 对外合集名称建议 |
| --- | --- | --- | --- |
| LLM | 模型有什么能力，模型本身为什么有这些能力？ | 模型发布、benchmark、实际能力、模型架构及相对前代的变化 | 大模型解析 / LLM |
| Harness | 围绕模型的 Agent 系统怎样工作？ | 上下文组织、会话压缩、记忆、工具执行、任务循环、权限、沙箱、通用执行机制 | Agent 工程 / Harness |
| 业务 Agent | Agent 怎样在真实业务中发挥作用并可靠运行？ | 企业场景、业务流程、系统接入、业务评测、上线前验证、线上故障、人工接管及改进 | 业务 Agent 实战 |

归类建议：每个选题保留一个主分组，可加多个标签。归类暂不明确时允许未分组，不阻止记录；跨领域题目按文章主问题确定主分组，不为每个涉及的概念复制一条选题。

例如，“记忆如何被提取和注入”归 Harness；“某业务 Agent 记错客户信息导致处理失败，怎样定位和改进”归业务 Agent。两篇都可以带“记忆”标签。

`Agent = LLM + harness` 可用作工程解释框架，不作为限制栏目设计的严格分类公式。业务 Agent 栏目按业务视角组织，即使文章涉及模型选型或 Harness 机制，也不需要因此改换主分组。

本地分组与平台合集名称分别记录。公众号和小红书可暂用同名，也允许以后分别改名。第一版只管理本地名称及拟归属，不创建、修改或同步平台合集；不假定账号已经创建合集。

## 行为建议

### 快速记录

- 只提供一个非空题目或一句想法即可记录，不要求同时提供完整大纲、来源和日期计划。
- 保留原始题意；Codex 可以提出更清楚的暂定标题，但不能用改写覆盖原意或把研究问题写成事实结论。
- 每项具有不随改标题、改分组而改变的标识，以及记录日期。
- 可补充主分组、标签、想回答的问题、资料链接、备注和关联内容项目。
- 新建时默认“待写”。资料核验情况记录在问题和备注中，避免把“待研究”与写作进度混成另一套流程。

### 查看与更新

- 可以查看全部选题，按分组、写作状态、关键词或它们的组合筛选。
- 列表至少展示可识别的选题标识、暂定题目、主分组、状态和简短角度；可继续读取某一条的完整备注与资料。
- 支持补充资料、修改题目、调整分组和状态。改分组名称后，原有选题仍能被找到，不因名称变化丢失关联。
- 更新目标不明确时先列出候选；不猜测后修改另一条选题。同名或近似题目可以是不同角度，不自动合并、覆盖或删除。
- 暂时不写的题目可以标为“暂缓”，之后仍可恢复。

建议使用四个状态：待写、写作中、已完成、暂缓。“已完成”表示作者确认该选题的写作工作已经完成，不表示公众号、小红书或网站已经发表。允许按实际情况调整状态，不设置强制审批流程。

### 衔接创作

- 仅登记选题时不生成正文，不自动创建一套三平台稿件。
- 用户明确开始某个选题的创作后，衔接已有 `content-projects/<id>/` 创作流程，并在选题中保留关联。
- 已有关联时继续已有内容项目，不重复创建；本轮只要求每个选题可关联一个内容项目，拆成系列时可以拆出后续选题。
- 内容项目仍管理工作稿、平台交付物和实际发布状态；选题库不另建一套平台发布账本。

## 约束与非目标

- 实际选题、研究笔记及未发布素材默认保留在项目本地，不进入 Git 或网站公开构建。可公开的使用说明与私人选题数据需要区分。
- 文件是持久记录来源；在同一项目开启新的 Codex 任务后，仍能读取已有选题，不依赖原聊天上下文或 Codex 跨任务记忆。
- 沿用当前内容准备、平台草稿和人工发表边界；登记、分组、更新状态或关联内容项目都不触发外部写操作。
- 第一版不包含自动搜集热点、定时提醒、排期日历、多人协作、自动评分、平台合集同步或自动发表。
- 本规格不规定数据格式、脚本命令或技能拆分；后续计划按最小必要实现决定。

## 验收标准

以下是待确认行为的验收草案，当前尚未执行功能验收。

- AC-1：用户只提供一个题目时，能够保存为待写选题；缺少分组、资料或大纲不阻止记录。随后在同一项目的新任务中可以读到该选题和原始题意。
- AC-2：根据本地初始选题记录完成初始化后，首批两个选题均可找到，分别归入 Harness 与 LLM；业务 Agent 分组可存在且没有虚构题目。名称采用用户最后确认版本。
- AC-3：用户要求查看某分组、某状态或某关键词的选题时，得到符合条件的记录；组合筛选同时满足条件，无结果时明确展示为空。
- AC-4：用户修改指定选题的标题、分组、状态或补充资料后，新任务读取到更新结果；无关字段和其他选题不被改动。分组改名后所属选题关联仍有效。
- AC-5：出现多个候选更新目标时，先显示候选让用户明确目标；确认前不写入任何候选。近似题目不会自动合并或覆盖。
- AC-6：选题暂缓后仍可查看并恢复；记录和修改状态不自动生成稿件，也不把“已完成”展示为任一平台已经发表。
- AC-7：用户开始写作时，可通过该选题找到新建或已有的内容项目；再次继续写作使用同一关联。既有工作稿和平台人工修改稿保留。
- AC-8：公众号与小红书的拟用合集名称可以分别记录和修改；本地改名不会造成平台写操作，也不会改变选题的主分组归属。
- AC-9：正常 Git 文件收集与网站公开构建不会纳入私人选题库、研究备注和未发布素材；选题管理不影响现有内容项目生成与草稿流程。
- AC-10：作者实际体验“记一个想法 → 按分组找到 → 补充资料 → 开始写作并找到内容项目”，确认能找回题意和资料，且无需在记录阶段填写完整文章信息。
